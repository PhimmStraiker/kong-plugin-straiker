# Claude Code wire ↔ Straiker hook mapping — analysis & learnings

The design of the `straiker-coding` plugin is driven by a corpus of real Claude
Code traffic captured through a gateway, with the native Straiker enforcement
hooks recording the same sessions in parallel. This documents what the corpus
showed and why the parser is built the way it is.

## Corpus

- **39 scenarios** driven headless (`claude -p`) through a byte-exact capture
  proxy, each an isolated session: file reads/writes/edits, Bash (short, long,
  failing), Grep/Glob, `Task` subagents, TodoWrite, MCP tool listing, multi-step
  tasks, and an attack battery (base64→bash, curl|sh, reverse shell, cred exfil,
  destructive rm, sensitive-file reads, indirect-injection via a poisoned file).
- Each session captured on **two** streams from the same run: the raw wire
  (`/v1/messages` requests + SSE responses) and the native Claude Code hook
  payloads (`UserPromptSubmit`/`PreToolUse`/`PostToolUse`/`Stop`).
- Corpus statistics (generated by `analyze_corpus.py`): 167 model calls across 39
  distinct sessions, 105 tool calls and 267 tool-result blocks. (Combined with the
  initial capture run, the micro-deliverable, and the live Kong runs, well over
  500 Claude Code messages were captured and analyzed.)

## What the wire looks like (the load-bearing facts)

1. **One developer action fans out into several model calls.** Even "echo hello"
   is 4 requests: a connectivity ping, a ~2 KB Haiku *title-generation* utility
   call, the ~138 KB main turn, and a follow-up carrying the tool result. A file
   read or multi-file task is 6–30+ calls.

2. **The main turn is dominated by scaffolding.** ~30 KB system prompt + 22 tool
   schemas + three `<system-reminder>` blocks. The actual user prompt is the
   **last text block of the last user message**, a few bytes at the end. This is
   why input/output guardrails false-positive: they score the scaffolding.

3. **The agentic loop resends the whole transcript every request.** Request N+1
   repeats the prompt, every prior `tool_use`, and adds the new `tool_result`.
   Naive per-request scoring double-counts everything → dedup is mandatory.

4. **Utility calls are structurally distinct: they carry zero tools.** Title
   generation, Haiku "suggestion mode", "user stepped away" recaps, and quota
   pings all have an empty `tools` array. Main turns always carry the full tool
   set. `n_tools == 0` is a clean, reliable chatter signal for Claude Code — the
   primary FP-suppression rule.

5. **Session identity is clean.** `metadata.user_id` is a JSON *string* holding
   `{"device_id":…, "session_id":"…"}`; the `session_id` is **constant across
   every request in the session**. This is the key for the backend's
   `hook_session:<straiker_id>:<app_id>:<user_name>:<session_id>` Redis trace —
   parsed directly, no heuristics.

6. **Responses are SSE (`text/event-stream`).** A `tool_use` block is assembled
   from `content_block_start{type:tool_use}` + a run of `input_json_delta`
   frames + `content_block_stop`. Text and tool_use interleave by index.

## The event-synthesis mapping

Per request/response cycle, emit in the native order
**PostToolUse → UserPromptSubmit → [response] → PreToolUse**:

| Hook event | Wire signal | Enforce? |
|---|---|---|
| `UserPromptSubmit` | last user **text** block, minus `<system-reminder>`/utility scaffolding | never blocks — starts the Redis trace |
| `PreToolUse` | assistant **`tool_use`** block in the response | block before the client executes it |
| `PostToolUse` | **`tool_result`** block in the next request, matched by `tool_use_id` | block the poisoned result reaching the model (stronger than the endpoint hook) |
| `Stop` | response `stop_reason: end_turn` with no tool_use | telemetry only (backend yields no `app_response`) |

Dedup keys (held in a `lua_shared_dict`, per session): `prompt:<md5>`,
`pre:<tool_use_id>`, `post:<tool_use_id>`. Each event is emitted once per session
regardless of how many times the transcript is resent.

Chatter filter (drop before `UserPromptSubmit`): zero-tool turns, plus verbatim
Claude-Code utility phrases (title-gen, suggestion mode, recap, compaction). The
markers are deliberately specific so a real prompt ("summarize the readme",
"check the quota") is never suppressed.

## Parity result (Kong-synthesized events vs native hooks)

`parity/parity_check.py` replays every captured wire session through the actual
plugin parser (`coding_agent.lua` + `sse.lua`, via `parity/lua_cli.lua`) and
diffs the synthesized events against the native hook events from the same
session. Results:

```
event              recall    precision   (kong / native / matched)
UserPromptSubmit   100.0%    95.1%       (41 / 39 / 39)
PreToolUse         100.0%    100.0%      (105 / 105 / 105)
PostToolUse        100.0%    91.4%       (105 / 96 / 96)
```

Reading the numbers:

- **`PreToolUse` is 100% / 100%.** The gateway captures every tool call the model
  emits, with the security-relevant `tool_input` fields identical to the native
  hook. (Matching is subset-based: the native hook additionally fills in client
  schema defaults the model never emitted — e.g. Edit's `replace_all: false` —
  which is not a capture miss.)
- **`PostToolUse` recall is 100%, precision 91.4%**: the 9 "extra" Kong events are
  the force-blocked / errored attack scenarios (bash_fail, cred_exfil, env_dump,
  rce_*, read_aws_creds, ipi_poisoned_read) where the native hook skips
  `PostToolUse` but the gateway still sees the error `tool_result` on the wire.
  The gateway is *more* complete, not less — every tool output is available to
  score.
- **`UserPromptSubmit` is 100% recall**; the 2 "extra" Kong events (precision
  95.1%) are subagent (`Task`) scenarios where the sub-agent issues its own
  prompt turn, which the gateway sees as a distinct `UserPromptSubmit`.

## Bedrock (the CVS transport)

Confirmed against live `bedrock-runtime`:

- **Request**: `POST /model/{modelId}/invoke-with-response-stream`, body in the
  **identical Anthropic Messages format** (`anthropic_version` + `system` +
  `tools` + `messages`). The request parser works unchanged.
- **Response**: `application/vnd.amazon.eventstream` — AWS binary framing whose
  inner chunks carry the **same** Anthropic message-stream events. `eventstream.lua`
  decodes the frames (verified on a real 9-frame / 3040-byte capture: recovered
  the `Bash {command:"ls -la"}` tool_use and `stop_reason: tool_use`), then the
  shared `sse.assemble_events` produces identical `PreToolUse` events.

Deployment note: routing Claude Code Bedrock traffic through Kong requires
SigV4 handling — the client signs for the AWS host, so Kong must re-sign (Kong's
`aws-request-signing` plugin) or the client sends unsigned to Kong which signs
with the real IAM credentials. The plugin's *parsing* is transport-agnostic.

## Efficacy vs blocking (an important, honest distinction)

- **Detection efficacy is proven and identical to the hooks path**: the same
  malicious `tool_input` posted with `x-tool: claude-code` scores the same
  category and score whether it came from the endpoint hook or the gateway
  (e.g. base64→bash → `RCE` 0.55, curl|sh → `RCE` 0.59, cred exfil →
  `Suspicious Outbound Access` 0.59).
- **Blocking depends on backend severity policy, not the plugin.** These
  rule-based coding-agent detections currently return `severity: low`, and the
  backend's block gate requires `high`/`critical`. So they *detect* but do not
  *block* by default — and this is true for the native hooks too (same pipeline).
  The plugin's block *plumbing* is proven end-to-end (a controlled deny through
  Kong replaced the tool call with an Anthropic block message; the tool never
  executed). Turning detections into blocks is a Console policy / severity-tuning
  exercise, out of scope for the gateway.
- **Claude models self-refuse obvious attacks.** In the corpus, Claude Code
  declined to emit the `tool_use` for base64→bash and curl|sh ("I can't run that
  command… a common pattern for hiding malicious commands"). So attack *detection*
  is best proven by posting the tool call directly (as the hooks and gateway
  both do); the corpus proves *benign/realistic* parity across the tool surface.

## Corpus statistics (`analyze_corpus.py`)

```
Total wire calls (model messages): 167   Distinct sessions: 39
By model: sonnet-4-5 = 163, haiku-4-5 = 4

Main turns (tool-bearing):     128 (76.6%)
Utility/chatter (zero-tool):    39 (23.4%)  -> all title-gen, dropped by chatter filter

System prompt size:  min 4 KB   median 30 KB   max 30 KB
Tools per request:   min 15     median 22      max 22
Main request size:   min 64 KB  median 140 KB  max 164 KB

Response transport:  SSE 167 / JSON 0
tool_use blocks (PreToolUse candidates):     105
tool_result blocks (PostToolUse candidates): 267   (deduped to 105 unique per session)
Tool usage: Bash 51, Read 36, Edit 11, TodoWrite 3, Write 2, Agent 2
```

The 23.4% zero-tool utility calls (all title generation here) are exactly the
class a naive gateway guardrail scores and false-positives on; the plugin drops
them before emitting `UserPromptSubmit`. The median 140 KB request with a 30 KB
system prompt and 22 tool schemas is the "verbose chatter" the customer's
existing tooling cannot parse — the plugin reads past it to the model's actual
tool calls.
